# Task 008: Move project, chapter, and node ID generation into command handlers

Use the **pi-ptdd** skill for this task. Assume tasks 001 through 005 are complete. This task should be done before relying further on multi-chapter graph editing, and preferably before task 006/007 if those have not already been implemented.

## Goal

Make project, chapter, and node identities opaque UUIDs generated by command handlers instead of UI/model code deriving IDs from currently projected state.

At the end of this task:

- adding nodes in different chapters cannot reuse the same `nodeId`
- project, chapter, and node creation commands generate UUID IDs through injectable generators
- UI/hooks/model code treats IDs as opaque strings and does not parse `node-1`, `chapter-1`, or similar counters for identity
- existing projected legacy IDs continue to work as opaque IDs
- tests pass

## Problem to fix

Task 005 exposed a projection bug when creating nodes in multiple chapters:

1. Empty Store
2. reload page
3. add node to default chapter
4. create new chapter
5. add node to new chapter
6. switch back to default chapter
7. no nodes displayed in default chapter
8. add node to default chapter
9. switch back to new chapter
10. no nodes displayed in new chapter

The likely cause is duplicate node IDs. Current app/model code generates node IDs from the active chapter's projected `snapshot.nodes`. Because each chapter can have an empty or independent projection, both chapters can create `node-1`. `GraphProjector` indexes nodes by `nodeId`, so replaying a later `NodeAdded` with the same `nodeId` overwrites earlier chapter membership and makes the other chapter appear empty.

## Required behavior

### ID generation

Creation command handlers must generate IDs using injectable UUID generators:

- `AddProject` generates `projectId`
- `AddChapter` generates `chapterId`
- `AddNodeCommand` generates `nodeId`
- `AddConnectedNodeCommand` generates the new connected `nodeId`

Tests should inject deterministic generators so assertions can verify exact IDs.

### Opaque ID handling

Production code must stop deriving identity from visible labels or parsed ID counters.

Remove identity logic like:

```ts
Number(node.id.replace('node-', ''))
```

Generating display labels such as `Node 1` may still use a separate counter if desired, but labels must not determine identity and duplicate labels must not corrupt projection.

### Backward compatibility

Existing stored/imported events with IDs such as `node-1`, `chapter-1`, `default-project`, or `default-chapter` must still project and mutate correctly. The change is about how new IDs are generated, not about rejecting legacy IDs.

### Bootstrap defaults

Choose one explicit approach and test it:

- either keep existing stable bootstrap IDs for the default project/chapter while all user-created IDs are UUIDs, or
- route bootstrap through the same command handlers and discover generated default IDs from workspace projection.

Prefer the smallest safe change unless the existing design already has default workspace command handling.

## Acceptance criteria

- A domain/model test proves adding one node to the default chapter, creating/selecting another chapter, adding a node there, and switching back preserves each chapter's own node.
- A domain/model test proves two nodes added in different chapters receive different `nodeId` values even when each chapter projection starts empty.
- A command-handler test proves `AddNodeCommand` uses an injected UUID generator for `nodeId`.
- A command-handler test proves `AddConnectedNodeCommand` uses an injected UUID generator for the new `nodeId` and connects to that generated ID.
- If `AddChapter` command handling exists, a test proves it uses an injected UUID generator for `chapterId`.
- If `AddProject` command handling exists, a test proves it uses an injected UUID generator for `projectId` and creates/links any initial chapter according to the current project creation design.
- A regression test proves legacy IDs still project as opaque strings.
- Focused search shows no remaining app/model identity generation based on parsing `node-<number>`, `chapter-<number>`, or `project-<number>` IDs.
