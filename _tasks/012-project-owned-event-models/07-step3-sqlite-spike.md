# Step 3: bounded SQLite event-store spike (not a format decision)

## Interface and layout

`@slicr/event-sourcing/sqlite` exports the Node-only `SqliteSpecEventStore<E>` adapter. `open(projectDirectory)` requires an existing store; `initialize(projectDirectory)` explicitly creates `.slicr/events.sqlite` and refuses an existing file. `open` uses Node 24 SQLite URI `mode=rw` for a writable no-create open, rather than an existence check followed by SQLite's creating default open. `initialize` constructs the database in a private directory, closes it, then atomically publishes it with a no-clobber hard link; a competing initializer cannot overwrite or initialize the winner's file. `close()` releases its connection. The browser-facing package root and IndexedDB implementation are unchanged. Requires Node 24+ for built-in `node:sqlite` `DatabaseSync` (not an npm SQLite driver); existing locked `@types/node` 24.12.4 is declared as a package dev dependency. No packages were installed for this spike.

Format v1 is a single SQLite database with `application_id=0x534c4352` (SLCR), `user_version=1`, and `events(position INTEGER PRIMARY KEY, event_json TEXT NOT NULL)`. Sequence positions start at 1, are globally ordered, and are never reused by this adapter. Event JSON is serialized with `JSON.stringify`; invalid JSON or missing `type`/`tags` on read fails with a position-specific corruption error. `open` verifies identity/version, exact table declaration, absence of unexpected triggers attached to `events`, and `PRAGMA quick_check`; foreign, incompatible, and malformed database files fail explicitly. Direct SQLite modification while the store is open is unsupported; schema validation runs at open, not per append. No automatic migration or rewrite.

## Transaction and evidence

A synchronous `BEGIN IMMEDIATE` obtains SQLite's write reservation _before_ evaluating the `AppendCondition` against all stored events after its optional position. The query matcher is shared with the memory and IndexedDB stores. All inserts for a batch and the condition check occur inside one transaction; success commits, failure rolls back. The conditional read is synchronous while the transaction is held, so overlapping calls on one instance cannot begin a nested transaction. SQLite's 5000 ms busy timeout bounds lock waiting; exhausted waits currently surface as SQLite errors, not an `AppendConditionFailedError`. Local subscriptions fire after commit only; there is no cross-process notification. Journal mode is DELETE to keep a single durable file after close (while active, a rollback journal can exist).

The initial spike ran on Node 24.21.0: `npm run test:llm --workspace=@slicr/event-sourcing -- --run src/sqliteSpecEventStore.test.ts` passed **10/10** before this follow-up; `npm run typecheck --workspace=@slicr/event-sourcing` passed. A direct Node 24.21.0 probe also confirmed `DatabaseSync(file:...?mode=rw)` writes an existing file and rejects a missing file without creating it. The added regressions cover concurrent conditional/unconditional appends on the same instance, no-create opening when `.slicr` already exists, simultaneous initialization by independent processes (one winner, one refused), and refusal to modify an existing foreign file. Tests exercise explicit initialization versus absent read (no `.slicr` created), ordered batch positions and replay after a _separate process_ reopens/appends, `read(from)` and query, stale conditional append with actionable `AppendConditionFailedError.conflictingEvents`, two independent processes both opening before a barrier and attempting conflicting writes (exactly one succeeds), rejection of an unexpected trigger on `events` at open, version/corruption errors, and local subscriptions. A shared empty-append contract test covers no condition conflict, no events, no notifications, and unchanged sequence numbering across memory, IndexedDB, and SQLite. Empty batches return before condition checks or writes. No trigger is part of the v1 layout. The initial spike's `npm run validate:llm` passed: formatting, lint, event-sourcing **69/69** (before this follow-up), other workspace tests/typechecks, and editor Playwright **3/3** (existing IndexedDB behavior). React-ui tests emitted pre-existing `act(...)` console warnings but passed. No manual editor smoke check was performed; this spike does not touch UI.

Follow-up verification on Node 24.21.0: focused SQLite/memory tests **13/13**, focused IndexedDB browser tests **6/6**, event-sourcing typecheck passed, and root `npm run validate:llm` passed (event-sourcing **71/71**, other workspace tests and typechecks, editor Playwright **3/3**). The first validation attempt failed lint because the shared test helper used `Query.all()` outside a `.test.ts` file; it was changed to a type-matching `Query.where(...)`, then full validation passed.

## Limits and open decisions

- This experiment does **not** select SQLite as the final project format. SQLite binary files do not merge meaningfully in Git; decide whether to Git-track the authoritative DB or instead track generated text and provide deliberate export/import. Do not treat generated text as a second authority.
- Back up using SQLite's online backup API or a quiesced, closed store copy; do **not** copy a live database file independently of an in-flight rollback journal. No backup/restore or crash/power-loss durability benchmark is implemented. Filesystem durability depends on SQLite and the host filesystem.
- JSON has no schema migration or domain validation here, and JSON serialization loses non-JSON values. Corruption checks are not a cryptographic event integrity proof and do not detect semantically altered but valid event rows. `quick_check` runs at every open and can be expensive for large histories.
- Full-history scans for query/condition and synchronous SQLite calls block the Node event loop. Measure realistic size and process contention before adoption. The 5000 ms lock timeout and read-only filesystem behavior need operational tests. No independent _crash-during-transaction_ or failed-batch rollback test is retained; the earlier trigger-based failure fixture conflicted with the supported schema/open contract.
- URI `mode=rw` prevents `open` from creating a missing file even if the path disappears while opening. Atomic no-clobber publication prevents cooperative initializers from claiming or modifying each other's files. This does **not** guarantee path identity against a hostile actor replacing a published file around `initialize`/`open`: inode checks catch observed replacements but cannot pin a pathname to a SQLite connection across all adversarial filesystem races. Hostile symlinks/path traversal and such replacement races remain untested and out of scope. Project path selection, CLI, migrations, projections, frontend wiring, and interprocess subscriptions remain out of scope.

**Recommendation:** retain as an isolated comparison candidate. Before Step 3 can be declared final, decide repository/backup policy and portability requirements, evaluate the remaining hostile-path identity risks for production, and test operational recovery and scale. Existing frontend remains on IndexedDB.
