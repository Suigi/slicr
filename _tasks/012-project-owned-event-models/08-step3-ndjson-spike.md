# Step 3: bounded NDJSON-authoritative outbox spike (not a format decision)

## Layout and protocol

`@slicr/event-sourcing/ndjson` is a separate Node 24-only `NdjsonSpecEventStore<E>` experiment; the prior SQLite adapter, browser entrypoint and IndexedDB remain unchanged. `initialize(project)` exclusively creates `.slicr/events.ndjson`; `open(project)` refuses an absent log without creating `.slicr`. Once the log exists, `open` creates/rebuilds `.slicr/events-outbox.sqlite` as needed. The log is the only replay authority. SQLite has one transient `outbox(slot=1, line)` row, not a second event table or editable history. Rebuilding requires **all writers stopped and the outbox empty**; deleting it with a pending row loses a batch (demonstrated in a test). Do not Git-track the runtime SQLite database.

Each newline-terminated JSON record is one whole batch (`v=1`, UUID batch ID, global first position, stable `batchId:index` event IDs, events, SHA-256 of the JSON payload). Positions start at 1 and advance per event. Replay validates version, shape, checksum, unique batch IDs and contiguous positions. A partial trailing record is _not_ a committed batch. If and only if its exact bytes prefix the staged outbox line, recovery truncates that tail, fsyncs the log, and republishes the complete line; an unmatched tail fails closed instead of guessing. One complete record per batch makes committed boundaries unambiguous; duplicate publication of a known batch ID verifies equality instead of appending it again.

Cooperating processes use SQLite `BEGIN IMMEDIATE` to serialize every read, conditional append and recovery. A writer repairs any pending row and reads the canonical log under that lock, checks the condition, allocates revision/IDs, and **commits** its staged row. It then reacquires the lock to publish (or observes that another participant has recovered the same row), fsyncs the NDJSON file, and acknowledges/removes the row. On later operations an existing canonical batch is recognized by ID and not republished. An append returns success only after durable log publication; listeners are local and notified after publication only. Empty appends are unconditional no-ops. Errors after staging can mean the batch was published despite an error response: consumers must read/reconcile instead of blindly retrying a command. SQLite's full synchronous rollback journal is used for staging; fsync and directory fsync are used for initial log creation. The log is appended in place, not rewritten during regular writes.

## Evidence

On Node 24.21.0, focused `npm run test:llm --workspace=@slicr/event-sourcing -- --run src/ndjsonSpecEventStore.test.ts` passed **10/10** and workspace typecheck passed after correction of staged-revision validation. Tests cover explicit initialization/no-artifact absent open, ordered multi-event replay after reopen, `read(from)`/query, empty append, two independent condition-checking processes (one winner), simulated failures after stage commit, after log fsync, and before acknowledgement commit (one logical batch on recovery), stable IDs, matching torn-tail repair versus unmatched-tail refusal, successful quiescent runtime DB deletion/rebuild, and the counterexample for deletion while pending. These are injected failures, **not** actual power-loss/kill-at-instruction durability tests. `npm run format` and root `npm run validate:llm` passed: event-sourcing **81/81**, other workspace tests **50/50, 47/47, 90/90, 5/5, 129/129**, editor Playwright **3/3**, lint and all typechecks. React UI emitted its existing `act(...)` warnings but tests passed. Dependencies were not installed; validation used a temporary symlink to an existing checkout's `node_modules`, removed afterward.

## Limits and recommendation

- **Deletion is conditional, not inherently safe.** A process or cleanup task that deletes the DB after stage commit but before log fsync destroys the only recoverable copy. The demonstration test deliberately violates this precondition and loses the batch. Concurrent runtime DB replacement also splits SQLite's lock domain across open handles; no inode/lease fencing or safe online deletion protocol is provided. The database is rebuildable only at a quiescent, verified-empty point; this is an operational requirement, not something the current API enforces. The outbox is transient coordination but temporarily holds data that has not yet reached the canonical authority.
- External Git edits, branches/merges, restoring older canonical files, log replacement, symlinks, hostile filesystem writes and concurrent manual SQLite editing are unsupported. The digest detects accidental corruption, not deliberate forgery. Arbitrary torn tails without a matching surviving outbox fail closed, not silently repaired. A crash during initialization after creating an empty log may leave an initialized empty project even if `initialize` threw. Multi-process subscription delivery and caller-supplied idempotency keys for retrying an _entire command_ are absent.
- All reads scan the full log under a synchronous cross-process SQLite lock. Large histories, busy timeouts, journal and fsync behavior on actual filesystems, power loss, permissions, and Git merge conflict resolution need evaluation. No domain event schema migration or non-JSON preservation. This is a spike, not production durability assurance.

**Recommendation:** do not select this as a final project format yet. The outbox protocol works for cooperative, stable-path processes while the runtime DB is retained through recovery, but cannot promise the proposed safety if the supposedly disposable outbox is removed mid-flight. Require a fenced quiescent cleanup protocol or a different authoritative write protocol, plus real crash/merge testing, before adoption.
